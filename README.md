# Mini NPU Simulator (E1-3)

MAC(Multiply-Accumulate) 연산으로 입력 패턴이 십자가(Cross)에 가까운지 X자에 가까운지
판별하는 Python 콘솔 애플리케이션이다.

- 파이썬 3.8 이상
- 외부 라이브러리 없음. 표준 라이브러리 `json`, `math`, `os`, `time`, `unicodedata`만 사용한다.
- 확인한 환경: macOS 27.0.1 (arm64), Python 3.14.8

---

### 미션 요구사항과 코드의 대응

| 미션 요구사항 | 어디서 처리하는가 |

| 최소 3×3, 5×5, 13×13, 25×25 처리 | 크기를 고정하지 않는다. `PERF_SIZES = [3, 5, 13, 25]`로 네 크기를 모두 돌린다 |
| 모드 1 입력 검증 후 재입력 유도 | `read_row`, `read_matrix` (3-1절) |
| 모드 1 필터 채우기 방식 선택 | `ask_filter_source` → 직접 입력 또는 생성기 (3-6절) |
| 모드 2 JSON 로드·스키마 검증 | `run_json_mode`, `load_filters`, `check_case` (3-4절) |
| 라벨 정규화 | `normalize_label` (3-2절) |
| MAC 연산을 반복문으로 직접 구현 | `mac` (3-1절) |
| 허용오차 기반 점수 비교 | `decide`, `EPSILON` (3-3절) |
| 크기별 평균 시간과 연산 횟수 표 | `print_performance`, `measure_ms` (3-5절) |
| 결과 리포트 (콘솔 + README) | `run_json_mode` 요약 + 이 문서 4절 |
| 보너스: 1차원 최적화 비교 | `mac_flat`, `flatten`, `print_optimization` (3-6절) |
| 보너스: 패턴 생성기 | `make_cross`, `make_x`. 모드 3(크기 N 입력), 모드 1 필터, 성능 분석 세 곳에서 쓴다 (3-6절) |

크기를 다루는 코드는 어디에도 3이나 25 같은 숫자를 박아두지 않았다.
`len(pattern)`으로 한 변의 길이를 읽어 쓰기 때문에, 5절에서 1000×1000까지
같은 코드로 돌릴 수 있었다. 모드 1만 미션 명세대로 3×3으로 고정돼 있다. 모드 1의 필터는
직접 입력과 패턴 생성기 중에 고를 수 있고, 임의의 N으로 생성해 보려면
모드 3을 쓴다(3-6절).

### 모드 3 - 패턴 생성기 (보너스)

크기 N을 입력하면 N×N 십자가와 X자를 만들고, 그 패턴을 그대로
MAC 판정과 성능 분석에 넘긴다. 생성기가 분석 경로에 실제로
연결돼 있다는 것을 한 화면에서 볼 수 있다.

```

#--------------------------------------

#--------------------------------------

  0 0 1 0 0

  0 1 0 1 0

#--------------------------------------

X 패턴 | Cross 점수 1.0 | X 점수 9.0 | 판정 X | 일치

#--------------------------------------
# [3] 성능 분석 (평균/10회)
#--------------------------------------

------------------------------
5x5   0.0014         25

#--------------------------------------

#--------------------------------------

----------------------------------
5x5   0.0014     0.0010     -28.1%
```

`[2]`의 판정은 생성기와 MAC 연산이 둘 다 맞는지 보는 자가 검사다.
생성한 패턴은 자기 쪽 필터에서 점수가 더 높아야 하므로,
`불일치`가 뜨면 둘 중 하나가 잘못된 것이다.

**크기 범위를 3~999 홀수로 둔 근거.** 하한 3은 미션이 정한 최소 크기다.
N이 1이면 십자가와 X자가 똑같은 행렬(`[[1.0]]`)이 되어 비교가 성립하지 않는다.
상한 999는 5절에서 측정해본 가장 큰 크기(1000) 아래의 홀수다.
더 큰 값도 돌아가지만 재본 적이 없어 받지 않는다.

**짝수를 막는 이유는 3-6절에 측정과 함께 적었다.** 짝수 N에서는 두 필터가
공평하지 않아서, 어느 쪽도 닮지 않은 입력까지 X로 판정된다.

25×25를 넘으면 행렬을 그대로 찍지 않고 1인 칸의 개수만 요약한다.
101×101이면 101줄이 나와 다른 출력을 밀어내기 때문이다.

```
크기 N (3~999 홀수): 101
Cross
  (101x101 라 생략. 값이 1인 칸 201개 / 전체 10201칸)
X
  (101x101 라 생략. 값이 1인 칸 201개 / 전체 10201칸)
```

| 대상 | 형식 | 예 | 이유 |
|---|---|---|---|
| MAC 점수 | 파이썬 기본 실수 표기 | `1.0`, `0.8999999999999999` | 자릿수를 깎으면 동점 판정의 근거가 화면에서 사라진다 |
| 연산 시간 | `ms` 단위, 소수점 4자리 | `0.0003 ms` | 3×3은 1마이크로초 미만이라 3자리면 `0.000`으로만 찍힌다 |
| 점수 차이 | 지수 표기, 유효숫자 4자리 | `1.110e-16` | 1e-16과 1e+1을 같은 표에 놓고 비교해야 한다 |
| 변화율 | 부호 포함 백분율, 소수점 1자리 | `-22.9%` | 측정할 때마다 몇 퍼센트씩 흔들려 더 깎을 의미가 없다 |
| 연산 횟수 | 정수 | `625` | N²은 항상 정수다 |
| 입력 행렬 확인 | 정수면 소수점 생략 | `1`, `0.5` | `1.0 0.0 1.0`보다 `1 0 1`이 패턴 모양을 보기 쉽다 |

점수만 자릿수를 고정하지 않은 것은 의도적이다. `0.9`와 `0.8999999999999999`를

판정됐는지 화면만 보고는 알 수 없게 된다.

표의 열 너비는 고정값이 아니라 내용에 맞춰 계산한다(`print_table`).
한글은 터미널에서 두 칸을 차지하므로 `len()` 대신 `display_width()`로
동아시아 문자 폭을 반영해 폭을 잰다. 그래서 값이 길어져도 열이 밀리지 않는다.

## 3. 구현 요약

### 3-1. MAC 연산

패턴과 필터를 같은 위치끼리 곱해서 전부 더한다. 두 행렬이 얼마나 겹치는지를
숫자 하나로 요약한 값이고, 이 값이 큰 쪽 필터가 패턴과 더 닮았다고 본다.

```python
def mac(pattern, matrix_filter):
    size = len(pattern)
    total = 0.0
    for row in range(size):
        for col in range(size):
            total += pattern[row][col] * matrix_filter[row][col]
    return total
```

- 벡터화 라이브러리를 쓰지 않고 이중 반복문으로 직접 돌린다.
- 누적 변수를 `0.0`으로 시작해서 입력이 정수여도 결과는 항상 실수로 나온다.
- N×N 입력이면 곱셈이 정확히 N²번 일어난다.

3×3 예시로 보면, 패턴이 X자(`101 / 010 / 101`)일 때
십자가 필터와는 가운데 한 칸만 겹쳐서 1.0, X자 필터와는 다섯 칸이 겹쳐서 5.0이 된다.
그래서 X자 쪽으로 판정된다.

**입력 값의 허용 범위와 경계 동작.**

| 입력 | 동작 | 비고 |
|---|---|---|
| 0, 1 | 정상 | 미션에서 다루는 기본 형태 |
| 임의의 실수 (`0.5`, `3.7`) | 정상 | `float()`로 파싱해 그대로 곱한다 |
| 음수 (`-1`) | 정상 | 점수를 깎는 방향으로 기여한다 |
| 지수 표기 (`1e-3`) | 정상 | `float()`가 받아들이는 표기는 모두 통과 |
| `inf`, `nan`, `1e400` | 거부 후 재입력 | `입력 형식 오류: 'nan' 는 사용할 수 없습니다. 유한한 숫자만 입력하세요.` |
| 숫자가 아닌 문자 | 거부 후 재입력 | `입력 형식 오류: 'x' 는 숫자가 아닙니다.` |
| 붙여쓴 숫자 (`010`) | 글자별로 쪼개 읽음 | 모든 글자가 숫자일 때만. `0.5`나 `-11`은 쪼개지 않는다 |
| 불리언 (`true`) | 모드 2에서 거부 | `is_square()`가 `bool`을 숫자에서 제외한다 |

`float()`은 `"inf"`와 `"nan"`도 정상적인 실수로 받아들인다. 처음에는 이것을
그대로 뒀는데, 실제로 넣어보니 두 가지 문제가 있었다.

- `print_matrix`가 행렬을 확인용으로 찍는 단계에서 `int(float("nan"))`이
  `ValueError`를, `int(float("inf"))`가 `OverflowError`를 내며
  **프로그램이 추적 메시지와 함께 멈췄다.** 점수를 계산하기도 전이다.
- 설령 통과시켜도 `nan`이 섞이면 점수가 `nan`이 되고,
  `nan`과의 비교는 전부 거짓이라 판정이 뜻을 잃는다.

그래서 **입력 단계에서 막는 쪽으로 바꿨다.** `read_row()`에서 `float()` 성공 후
`math.isfinite()`로 확인하고, 유한하지 않으면 그 줄을 다시 받는다.
`1e400`처럼 범위를 넘어 `inf`가 되는 표기도 같이 걸린다.
`format_number()`에도 같은 검사를 넣어, 다른 경로로 들어오더라도
출력 단계에서 죽지 않게 했다.

모드 2는 JSON이라 `inf`/`nan` 표기가 표준에 없고, `is_square()`가
`int`/`float`만 통과시키면서 `bool`은 걸러낸다. 파이썬에서 `True`는 `int`의
하위 타입이라 타입 검사만 하면 숫자로 취급되기 때문에 따로 제외했다.

**점수의 스케일과 해석 한계.**

MAC 점수는 정규화되지 않은 값이다. 같은 모양이라도 패턴의 값이 두 배가 되면
점수도 두 배가 되고, 크기가 커지면 겹치는 칸 수가 늘어 점수가 커진다.
실제로 이 데이터에서도 `size_5_2`는 8.9, `size_25_2`는 52.9로 자릿수가 다르다.

그래서 **점수의 절대값은 의미가 없고, 같은 패턴에 대한 Cross 점수와 X 점수의
대소 관계만 의미가 있다.** 다른 크기나 다른 패턴끼리 점수를 비교하면 안 된다.

실제 데이터로 보면 이렇다.

| 케이스 | Cross 점수 | X 점수 | 판정 |
|---|---|---|---|
| size_5_2 | 8.9 | 0.1 | Cross |
| size_25_2 | 52.9 | 0.1 | Cross |

둘 다 십자가로 올바르게 판정된다. 그런데 `size_5_2`의 Cross 점수 8.9는
`size_25_2`의 X 점수 0.1보다 크다. 여기서 "8.9 > 0.1이니 size_5_2가
size_25_2보다 더 X자답다"고 읽으면 완전히 틀린다. 두 숫자는 애초에
크기가 다른 필터에서 나온 값이라 같은 자 위에 놓을 수 없다.
비교가 성립하는 것은 **같은 행에 있는 두 점수 사이뿐**이다.
코사인 유사도처럼 크기에 무관한 지표를 쓰면 비교가 가능해지지만,
제곱근 연산이 들어가 MAC만으로 끝나지 않으므로 미션 범위에서는 쓰지 않았다.

### 3-2. 라벨 정규화

`data.json`은 같은 뜻을 두 가지 표기로 쓴다.

| 위치 | 표기 | 표준 라벨 |
|---|---|---|
| `patterns[*].expected` | `'+'` | `Cross` |
| `patterns[*].expected` | `'x'` | `X` |
| `filters[size_N]` 키 | `'cross'` | `Cross` |
| `filters[size_N]` 키 | `'x'` | `X` |

표기가 섞인 채로 비교하면 `'+' == 'cross'`가 거짓이라 멀쩡한 케이스도 FAIL이 된다.
그래서 읽어 들이는 지점에서 전부 표준 라벨 2개(`Cross`, `X`)로 바꾸고,
그 뒤의 판정·출력·PASS/FAIL 비교는 모두 표준 라벨만 쓴다.

```python
def normalize_label(raw):
    if not isinstance(raw, str):
        return None
    text = raw.strip().lower()
    if text in ("+", "cross", "plus"):
        return CROSS
    if text == "x":
        return X_MARK
    return None
```

**받아들이는 표기 전체 목록.** 앞뒤 공백을 지우고 소문자로 바꾼 뒤 비교하므로,
대소문자와 양끝 공백은 어느 표기에서나 무시된다.

| 표준 라벨 | 받아들이는 표기 | 공백·대소문자 변형 예 |
|---|---|---|
| `Cross` | `+`, `cross`, `plus` | `Cross`, `CROSS`, `' cross '`, `' + '` |
| `X` | `x` | `X`, `' x '` |

`plus`는 미션 데이터에 없지만 `+`의 영문 이름이라 함께 받도록 했다.
그 밖의 표기(`십자`, `cross_filter`, `1`, `null`, 숫자 타입 등)는 전부 거부한다.
문자열이 아닌 값은 `isinstance` 검사에서 먼저 걸러 `.lower()` 호출로
예외가 나는 일이 없다.

**정규화에 실패하면 어떻게 되는가.** 실패는 예외를 던지지 않고 `None`으로 표현한다.
부른 쪽이 그 `None`을 보고 해당 케이스만 FAIL로 처리한다. 흐름은 두 갈래다.

```
expected 값이 정규화 실패
  normalize_label() -> None
  check_case()가 (None, "expected 값 '세모' 를 표준 라벨로 바꿀 수 없음") 반환
  run_json_mode()가 "판정: FAIL (사유)" 출력
  failures 목록과 '데이터/스키마 오류' 카운터에 기록
  다음 케이스로 계속 진행 (프로그램은 멈추지 않는다)

filter 키가 정규화 실패
  normalize_label() -> None
  load_filters()가 "경고: 필터 'size_5' 의 라벨 'plus_sign' 를 알 수 없어 건너뜁니다." 출력
  해당 라벨만 제외하고 나머지 필터는 그대로 로드
  그 크기의 패턴은 check_case()에서 "Cross/X 가 모두 있지 않음"으로 FAIL
```

두 경로 모두 공통점은 **문제를 조용히 넘기지 않고 사유를 남기되,
전체 실행은 계속한다**는 것이다. 케이스 하나의 데이터가 깨졌다고
나머지 다섯 개의 판정 결과를 못 보게 되면 디버깅이 더 어려워진다.

**새 라벨을 추가하려면.** 예를 들어 `O`(동그라미) 라벨을 추가한다고 하면
다음 순서로 고치면 된다.

1. `main.py` 상단에 표준 라벨 상수를 추가한다. (`O_MARK = "O"`)
2. `normalize_label()`에 받아들일 표기를 추가한다. (`if text in ("o", "circle"): return O_MARK`)
3. `make_circle(size)` 같은 필터 생성기를 추가한다. (패턴 생성기를 쓰는 경우)
4. `check_case()`의 필터 존재 검사에 새 라벨을 포함시킨다.
   지금은 `CROSS not in table or X_MARK not in table`로 두 개를 확인한다.
5. `decide()`를 두 점수 비교에서 여러 점수 중 최대값 선택으로 바꾼다.
   이때 **최대값이 두 개 이상이면 UNDECIDED**라는 규칙을 유지해야 한다.
6. `test_main.py`에 테스트를 추가한다.
   - `TestNormalizeLabel`에 새 표기가 `O`로 바뀌는지 확인하는 테스트
   - `TestDecide`에 세 점수 중 최대값을 고르는지, 최대가 둘이면 UNDECIDED인지 확인하는 테스트
   - `TestGenerator`에 새 패턴이 자기 필터에서 점수가 가장 높은지 확인하는 테스트
7. `python3 -m unittest -v`로 전부 통과하는지 확인한 뒤,
   `data.json`에 새 라벨 케이스를 넣고 모드 2를 실행해 판정이 나오는지 본다.

지금 구조에서 2번과 6번만으로 끝나지 않는 이유는 `decide()`가 두 점수 비교로
고정돼 있기 때문이다. 라벨이 두 개라는 전제가 미션 요구사항이라 일부러
일반화하지 않았다.

### 3-3. 동점 처리 (epsilon)

두 점수를 `==`로 비교하면 안 된다. 부동소수점은 10진 소수를 2진으로 정확히
표현하지 못해서, 수학적으로 같은 값도 계산 순서에 따라 마지막 자리가 달라진다.

```
>>> 0.3 + 0.3 + 0.3
0.8999999999999999
>>> 0.3 + 0.3 + 0.3 == 0.9
False
```

그래서 차이가 허용오차보다 작으면 같다고 본다.

```python
EPSILON = 1e-9

def decide(score_cross, score_x):
    if abs(score_cross - score_x) < EPSILON:
        return UNDECIDED
    if score_cross > score_x:
        return CROSS
    return X_MARK
```

**EPSILON 값을 바꾸면 결과가 어떻게 달라지는가.** 제공된 `data.json` 6개 케이스로
`EPSILON`만 바꿔가며 재실행한 결과다.

| EPSILON | PASS | FAIL | 동점 판정 수 | 비고 |
|---|---|---|---|---|
| 0.0 (허용오차 없음) | 3 | 3 | 0 | 단순 `>` 비교와 같다 |
| 1e-18 | 3 | 3 | 0 | 오차보다 작아 아무것도 못 잡는다 |
| 1e-15 | 3 | 3 | 1 | 세 동점 중 하나만 잡힌다 |
| 1e-12 | 3 | 3 | 3 | 세 동점을 모두 잡는다 |
| **1e-9 (현재)** | **3** | **3** | **3** | |
| 1e-6 | 3 | 3 | 3 | |
| 1.0 | 3 | 3 | 3 | |
| 10.0 | 2 | 4 | 4 | 차이 8.8인 정상 케이스까지 동점 처리 |
| 100.0 | 0 | 6 | 6 | 전부 동점이 되어 판정이 무의미해진다 |

이 데이터에서 두 점수의 차이는 두 덩어리로 완전히 갈린다.

```
size_5_1    1.110e-16
size_25_1   1.776e-15
size_13_2   2.665e-15     <- 여기까지가 동점 케이스
size_5_2    8.800e+00
size_13_1   1.440e+01
size_25_2   5.280e+01     <- 여기부터가 정상 케이스
```

2.7e-15와 8.8 사이에 15자리 가까운 빈 구간이 있고, `1e-12`부터 `1.0`까지
어떤 값을 골라도 결과가 똑같다. `1e-9`는 이 안전 구간의 한가운데에 있다.
값을 1000배 키우거나 1000배 줄여도 판정이 바뀌지 않는다는 뜻이라,
측정 환경이나 데이터가 조금 달라져도 흔들리지 않는다.

**왜 하필 1e-9인가.** 이 문제에서 다루는 점수 범위는 0에서 수백 사이다.
배정밀도 실수의 상대 오차는 약 2.2e-16이므로, 점수가 625일 때
누적 오차는 커봐야 `625 × 2.2e-16 ≈ 1.4e-13` 수준이다.
`1e-9`는 그보다 네 자리 크고, 의미 있는 점수 차이(최소 0.1 단위)보다는
여덟 자리 작다. 양쪽 모두에 여유가 있다.

**모드 1과 모드 2의 처리가 다른 이유.** 같은 `EPSILON`을 쓰지만 결과 표기가 다르다.

| | 모드 1 | 모드 2 |
|---|---|---|
| 동점일 때 출력 | `판정: 판정 불가 (\|A-B\| < 1e-09)` | `판정: UNDECIDED \| expected: X \| FAIL (동점 규칙)` |
| 집계 | 없음 | FAIL로 세고 사유별 카운터에 기록 |
| 비교 대상 | 없음 (정답이 주어지지 않는다) | `expected` |

모드 1은 사용자가 방금 넣은 필터 두 개를 비교하는 것이라 정답이 없다.
그래서 "둘 중 어느 쪽인지 말할 수 없다"는 사실만 알리면 된다.
모드 2는 `expected`라는 정답이 있고 PASS/FAIL을 집계해야 하므로,
동점을 `UNDECIDED`라는 제3의 판정으로 명시하고 `expected`와 다르니 FAIL로 센다.
판정 로직(`decide`)은 하나를 공유하고 표기와 집계만 모드별로 다르게 한 것이다.

### 3-4. 스키마 검증

필터와 패턴은 바깥에서 들어오는 데이터라서 믿고 쓰지 않는다.
검사해서 어긋나면 그 케이스만 FAIL로 처리하고 다음 케이스로 넘어간다.

**`data.json`이 따르는 구조.**

```json
{
  "meta": { "version": "1.0", "type": "json" },
  "filters": {
    "size_5":  { "cross": [[...5개...], ... 5줄 ...],
                 "x":     [[...5개...], ... 5줄 ...] },
    "size_13": { "cross": [...13x13...], "x": [...13x13...] },
    "size_25": { "cross": [...25x25...], "x": [...25x25...] }
  },
  "patterns": {
    "size_5_1":  { "input": [...5x5...],   "expected": "x" },
    "size_5_2":  { "input": [...5x5...],   "expected": "+" },
    "size_13_1": { "input": [...13x13...], "expected": "x" },
    "size_25_2": { "input": [...25x25...], "expected": "+" }
  }
}
```

- `meta`는 읽지 않는다. 없어도 동작한다.
- `filters`의 키 `size_N`에서 N을 뽑아 그 크기의 필터로 쓴다.
- `patterns`의 키 `size_N_{번호}`에서 같은 방식으로 N을 뽑아
  `filters["size_N"]`과 짝지운다. 즉 패턴과 필터를 연결하는 것은
  별도 참조 필드가 아니라 **키 이름에 들어 있는 숫자**다.

읽어 들인 뒤 프로그램 안에서는 아래 형태로 바뀐다. 키가 문자열이 아니라
정수이고, 라벨은 표준 라벨로 통일된 상태다.

```python
filters = {
    5:  {"Cross": [[...]], "X": [[...]]},
    13: {"Cross": [[...]], "X": [[...]]},
    25: {"Cross": [[...]], "X": [[...]]},
}
```

**검사 항목과 실패 시 동작.**

| 검사 항목 | 어긋났을 때 |
|---|---|
| 최상위가 객체 형식인가 | 안내 후 메뉴로 복귀 |
| `patterns`가 객체 형식인가 | 안내 후 메뉴로 복귀 |
| 필터 키에서 크기를 읽을 수 있는가 | 경고 후 그 필터 제외 |
| 필터 행렬이 N×N 숫자 배열인가 | 경고 후 그 라벨 제외 |
| 같은 크기의 필터가 이미 로드됐는가 | 경고 후 덮어씀 (어느 쪽이 쓰였는지 알리기 위함) |
| 패턴 키에서 크기를 읽을 수 있는가 | 케이스 FAIL, 사유 기록 |
| 패턴 항목이 객체 형식인가 | 케이스 FAIL, 사유 기록 |
| `input`이 N×N 숫자 배열인가 | 케이스 FAIL, 사유 기록 |
| `expected`를 표준 라벨로 바꿀 수 있는가 | 케이스 FAIL, 사유 기록 |
| 해당 크기의 필터가 있는가 | 케이스 FAIL, 사유 기록 |
| 필터에 Cross와 X가 모두 있는가 | 케이스 FAIL, 사유 기록 |

**키 해석(`parse_size`)이 실패하는 경우.** `size_N` 또는 `size_N_번호` 형태가
아니면 `None`을 돌려준다.

| 키 | 결과 | 출력되는 메시지 |
|---|---|---|
| `size_13` | 13 | (정상) |
| `size_25_4` | 25 | (정상) |
| `filter_5` | None | `판정: FAIL (패턴 키 'filter_5' 에서 크기를 읽을 수 없음)` |
| `size_abc` | None | `판정: FAIL (패턴 키 'size_abc' 에서 크기를 읽을 수 없음)` |
| `size_0`, `size_-3` | None | 0 이하는 행렬로 성립하지 않아 거부한다 |
| `size` | None | `판정: FAIL (패턴 키 'size' 에서 크기를 읽을 수 없음)` |

### 3-5. 시간 측정

I/O가 섞이면 연산 시간이 아니라 터미널 출력 시간을 재게 된다.
그래서 입력·출력·파일 읽기는 측정 구간 밖에 두고, 연산 함수 호출만 감쌌다.

```python
REPEAT = 10
WARMUP = 1

def measure_ms(function, left, right, repeat=REPEAT, warmup=WARMUP):
    for _ in range(warmup):
        function(left, right)
    start = time.perf_counter()
    for _ in range(repeat):
        function(left, right)
    elapsed = time.perf_counter() - start
    return (elapsed / repeat) * 1000
```

- `time.time()` 대신 `time.perf_counter()`를 썼다. 벽시계와 달리
  중간에 시스템 시각이 바뀌어도 영향을 받지 않고 해상도가 더 높다.
- 한 번만 재면 편차가 커서 미션 기준대로 10회 반복 후 평균을 낸다.

**워밍업 횟수를 1로 둔 근거.** 첫 호출은 패턴과 필터 데이터가 CPU 캐시에
올라와 있지 않아 느리다. 워밍업 없이 10회 평균을 내면 그 한 번이 평균을 끌어올린다.
그게 실제로 일어나는지 25×25로 워밍업 횟수만 바꿔가며 재봤다.

**처음 측정은 설계가 틀렸다.** 0회를 9번, 그다음 1회를 9번, 하는 식으로
한 조건을 몰아서 쟀다. 그렇게 나온 표가 이것이다.

| 워밍업 | 평균 시간(ms) | 최소 | 최대 |
|---|---|---|---|
| 0회 | 0.0156 | 0.0151 | 0.0162 |
| 1회 | 0.0152 | 0.0151 | 0.0158 |
| 2회 | 0.0145 | 0.0143 | 0.0150 |
| 5회 | 0.0146 | 0.0142 | 0.0147 |
| 10회 | 0.0141 | 0.0140 | 0.0142 |

워밍업을 늘릴수록 10% 낮아지는 깔끔한 경향으로 보인다. 그런데
다시 재면 이 표가 나오지 않았고, 어떤 실행에서는 오히려 1.2% **올라갔다**.

**원인은 측정 순서였다.** 워밍업을 늘리는 순서대로만 쟀기 때문에,
측정이 진행되는 동안 기기 상태가 변하는 것(드리프트)이
그대로 "워밍업 효과"처럼 보인다. 나중에 재는 조건일수록 유리하거나
불리해지는 것뿐인데 둘을 구분할 방법이 없었다.

**그래서 측정 설계를 바꿨다.** 워밍업 횟수들을 **한 라운드 안에서 번갈아 재고,
라운드마다 순서를 섞는다.** 그러면 드리프트가 모든 조건에 고르게 퍼져
상쇄되고, 남는 차이만 워밍업 효과로 읽을 수 있다.

```python
WARMUP_COUNTS = (0, 1, 2, 5, 10)
order = list(WARMUP_COUNTS)
for _ in range(rounds):
    random.shuffle(order)
    for warmup in order:
        samples[warmup].append(main.measure_ms(..., warmup=warmup))
```

판정 기준도 같이 바꿨다. 워밍업별 중앙값의 폭을, **같은 조건을 9번
되풀이했을 때의 흔들림**과 비교한다. 중앙값 차이가 흔들림보다 작으면
그 차이는 잡음 안에 있다는 뜻이라 효과라고 부를 수 없다.

**고친 설계로 세 번 재면 이렇게 나온다**(`python3 benchmark.py 워밍업`).

| | 실행 1 | 실행 2 | 실행 3 |
|---|---|---|---|
| 0회 | 0.0169 | 0.0126 | 0.0126 |
| 1회 | 0.0168 | 0.0126 | 0.0127 |
| 2회 | 0.0167 | 0.0126 | 0.0127 |
| 5회 | 0.0168 | 0.0126 | 0.0127 |
| 10회 | 0.0159 | 0.0126 | 0.0130 |
| **0회 대비 10회** | **−5.4%** | **−0.1%** | **+3.1%** |
| 중앙값의 최대-최소 폭 | 0.0009 ms | 0.0001 ms | 0.0004 ms |
| 같은 조건 9회의 흔들림 | 0.0021 ms | 0.0011 ms | 0.0006 ms |
| 폭 < 흔들림인가 | 예 | 예 | 예 |

**세 번 모두 워밍업별 차이가 같은 조건의 흔들림보다 작다.**
변화 방향도 −5.4%, −0.1%, +3.1%로 일정하지 않다.
즉 순서를 섞어 드리프트를 걷어내고 나면 **이 작업 부하에서
워밍업 효과는 확인되지 않는다.** 처음 표에서 본 10% 하강은
워밍업이 아니라 측정 순서가 만든 것이었다.

25×25 행렬 두 개는 수 KB라 첫 호출에서도 캐시에 금방 올라간다.
워밍업이 의미를 가지려면 데이터가 캐시에 안 들어갈 만큼 커야 하는데,
미션이 다루는 크기에서는 그렇지 않다는 설명과도 맞는다.

**그래서 `WARMUP = 1`을 그대로 뒀다.** 효과가 없는 것으로 측정됐으니
0으로 둬도 되지만, 비용이 호출 한 번뿐이고 더 큰 입력에서는
첫 호출이 느릴 수 있으므로 값싼 안전장치로 남겼다.
**측정해보지 않고 둔 값이 아니라, 재서 차이가 없음을 확인하고 둔 값이다.**

`WARMUP`은 상수로 빼뒀고 `measure_ms`의 인자로도 받는다.
`measure_ms(mac, pattern, matrix_filter, warmup=10)`처럼 호출하면
워밍업 횟수를 바꿔 직접 확인할 수 있다.

### 3-6. 보너스

**패턴 생성기.** 크기 N을 주면 N×N 십자가와 X자를 만든다.

```python
def make_cross(size):   # 가운데 행과 가운데 열이 1
def make_x(size):       # 두 대각선이 1
```

미션은 "크기 N 입력 시 자동 생성"과 "생성된 패턴을 모드 1/성능 분석에
재활용"을 함께 요구한다. 그래서 쓰이는 곳이 세 군데다.

- **모드 3 (크기 N 입력)** — `ask_size()`로 N을 받아 `make_cross(N)`,
  `make_x(N)`을 만들고 그대로 MAC 판정과 성능 분석까지 넘긴다.
- **모드 1** — `ask_filter_source()`에서 `2`를 고르면
  `make_cross(3)`과 `make_x(3)`이 필터 A와 B를 채운다.
- **성능 분석** — `print_performance`와 `print_optimization`이
  3×3, 5×5, 13×13, 25×25 입력을 만들 때 이 함수를 쓴다.

처음에는 성능 분석에서만 썼다. 모드 1에서 9칸을 두 번 입력해야
표준 필터 비교를 볼 수 있는 것이 불편해 먼저 모드 1에 연결했고,
N을 직접 넣어 생성 결과를 확인할 경로가 없다는 것을 알고 모드 3을 더했다.
세 경로 모두 테스트로 고정해뒀다
(`test_모드1에서_생성기로_필터를_채울_수_있다`,
`test_모드3은_크기를_받아_생성하고_판정까지_간다`, `TestGenerator`).

**모드 3이 홀수만 받는 이유.** 모드 3을 붙이고 나서 짝수 N을 넣어보니
두 필터가 공평하지 않았다. 원인이 둘이다.

- **십자가가 비대칭이 된다.** 가운데 행을 `size // 2`로 고르는데,
  짝수면 진짜 가운데가 없다. N=10이면 5번 행이 선택되어
  위로 5줄, 아래로 4줄이 남는다. 십자가라고 부르기 어려운 모양이다.
- **X자의 1인 칸이 하나 더 많아진다.** 두 대각선이 중앙에서 겹쳐야
  `2N-1`인데, 짝수면 겹치는 칸이 없어 `2N`이 된다.
  십자가는 가운데에서 행과 열이 항상 겹치므로 `2N-1` 그대로다.

필터 한쪽이 1칸 무거우면 **어느 쪽도 닮지 않은 입력이 무거운 쪽으로 기운다.**
전부 1인 패턴(어느 쪽과도 똑같이 겹친다)과 무작위 0/1 패턴 200개로 확인했다.

| N | 십자가 1인 칸 | X자 1인 칸 | 전부 1인 패턴의 판정 | 무작위 200개 (Cross승 / X승 / 동점) |
|---|---|---|---|---|
| 5 | 9 | 9 | UNDECIDED | 80 / 89 / 31 |
| **10** | 19 | **20** | **X** | **66 / 111 / 23** |
| 11 | 21 | 21 | UNDECIDED | 81 / 94 / 25 |
| 25 | 49 | 49 | UNDECIDED | 85 / 100 / 15 |
| **26** | 51 | **52** | **X** | **78 / 107 / 15** |
| 101 | 201 | 201 | UNDECIDED | 96 / 96 / 8 |

홀수에서는 전부 1인 패턴이 `UNDECIDED`로 나온다. 어느 쪽도 더 닮지
않았다는 사실이 그대로 드러난다는 뜻이다. 짝수에서는 같은 입력이 `X`로
판정되고, 무작위 패턴에서도 X가 눈에 띄게 유리하다(N=10에서 66 대 111).

**그래서 모드 3은 짝수를 받지 않고, 이유와 함께 가까운 홀수를 알려준다.**
미션이 쓰는 크기(3, 5, 13, 25)가 전부 홀수라 기존 경로에서는 드러나지 않던
문제였고, 임의의 N을 받는 모드 3을 만들면서 보이게 된 것이다.
이 성질은 `TestGeneratorFairness`로 고정해뒀다. 짝수 쪽 동작까지 테스트에
남겨서, 생성기를 고쳐 공평해지면 제한도 다시 보게 했다.

**1차원 배열 최적화.** 2차원 인덱싱 `matrix[row][col]`은 바깥 리스트에서
행 리스트를 찾고 거기서 다시 값을 찾는 2단계다. 미리 길이 N²의 1차원 배열로
펴두면 1단계로 줄어든다. 곱셈 횟수는 N²로 똑같고 메모리 접근 방식만 바뀐다.
모드 2에서 두 방식을 같은 입력·같은 반복 횟수로 비교해 출력한다.

실패 원인은 "데이터/스키마 문제", "로직 문제", "수치 비교 문제" 셋으로 나눠 볼 수 있다.
이번 FAIL 3건은 전부 **수치 비교 문제**이고, 스키마 문제나 로직 문제는 없다.
프로그램도 이 분류대로 세서 요약에 찍는다(동점 3 / 라벨 불일치 0 / 데이터·스키마 0).

**스키마 문제가 아닌 이유.** 6개 모두 `input`이 키에 적힌 크기와 같은 N×N 숫자 배열이고,
`expected`도 `'+'` 또는 `'x'`로 정규화 가능한 값이다. `filters`에는 `size_5`, `size_13`,
`size_25`가 모두 있고 각각 `cross`, `x` 키를 가진다. 검증 단계에서 걸러지는 케이스가 없다.

**로직 문제가 아닌 이유.** PASS 3개는 점수 차이가 8.8, 14.4, 52.8로 커서
MAC 연산과 비교가 의도대로 동작한다는 걸 보여준다.

**그럼 FAIL 3개는 무엇인가.** 세 케이스 모두 Cross 점수와 X 점수가
소수점 15~16번째 자리에서만 다르다. 이게 부동소수점 오차 때문인지,
아니면 실제로 조금 다른 값인지 확인하려고 같은 계산을 유리수(`fractions.Fraction`)로
한 번 더 돌려봤다. 각 칸의 값을 10진 문자열로 바꿔 분수로 곱하고 더하면 오차가 끼지 않는다.

| 케이스 | float Cross | float X | 유리수 Cross | 유리수 X |
|---|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | 9/10 | 9/10 |
| size_13_2 | 7.499999999999997 | 7.5 | 15/2 | 15/2 |
| size_25_1 | 4.9 | 4.899999999999999 | 49/10 | 49/10 |

오차 없이 계산하면 세 케이스 모두 **두 점수가 정확히 같다**.
즉 이건 계산 실수가 아니라 Cross와 X 중 어느 쪽도 더 닮았다고 말할 수 없는 입력이다.
`0.1`, `0.3` 같은 10진 소수는 2진 부동소수점으로 정확히 표현되지 않아서,
더하는 순서가 다르면 마지막 자리가 달라진다. 그 차이가 그대로 점수 차이로 보이는 것뿐이다.

**허용오차를 안 썼다면 어떻게 됐을까.** `>` 로만 비교했다면 이렇게 판정된다.

| 케이스 | 단순 비교 판정 | expected | 결과 |
|---|---|---|---|
| size_5_1 | Cross (0.9 > 0.8999…) | X | FAIL |
| size_13_2 | X (7.5 > 7.4999…) | Cross | FAIL |
| size_25_1 | Cross (4.9 > 4.8999…) | X | FAIL |

세 경우 모두 `expected`의 반대로 판정된다. 3-3절의 민감도 표에서
`EPSILON = 0.0`일 때 PASS가 그대로 3인 것이 이 결과다.
**허용오차를 없애도, 줄여도 통과 개수는 늘지 않는다.**
바꿀 수 있는 것은 통과 개수가 아니라 같은 결과를 어떤 근거로 내놓느냐뿐이다.
단순 비교는 1e-16짜리 쓰레기 자리를 근거로 틀린 라벨을 확신해서 내놓고,
허용오차 비교는 근거가 없다는 사실을 UNDECIDED로 드러낸다.
후자는 점수와 차이값을 함께 출력하므로 왜 판정이 안 되는지 사람이 바로 확인할 수 있다.

`expected`가 전부 단순 비교의 반대 라벨로 적혀 있다는 점도 눈에 띈다.
마지막 자리 오차를 믿고 판정하면 틀린다는 걸 보여주려고 만들어진 데이터로 보인다.

**그래서 이 FAIL은 고치지 않았다.** 통과 개수를 늘릴 방법이 없고,
억지로 바꾸려면 데이터 자체를 손대야 하는데 그건 판정기를 고치는 게 아니다.
미션 권장 기준인 `1e-9`를 그대로 두고, 동점은 동점이라고 보고하는 쪽을 택했다.

**정리.**

- FAIL 3건: 수치 비교 문제. 두 점수가 수학적으로 같은 입력이고,
  허용오차 정책에 따라 UNDECIDED로 판정되어 `expected`와 불일치.
- 데이터/스키마 문제: 0건. 6개 전부 크기와 라벨이 맞다.
- 로직 문제: 0건. 점수 차이가 뚜렷한 케이스는 전부 정확히 판정된다.
- 라벨 정규화가 없었다면 여기에 FAIL이 2건 더 늘었을 것이다
  (`'+'`와 `'Cross'`를 다른 값으로 보게 되어 `size_5_2`, `size_25_2`가 뒤집힌다).

### 4-3. 성능 표와 시간 복잡도

아래 수치는 **`python3 benchmark.py`를 한 번 실행한 출력을 그대로 옮긴 것**이다.
같은 명령으로 다시 만들 수 있다. 2절의 콘솔 예시는 `main.py`를 따로 돌린
것이라 소수점 끝자리가 다르다.

| 크기 (N×N) | 평균 시간 (ms) | 1차원 버전 (ms) | 변화율 | 연산 횟수 (N²) |
|---|---|---|---|---|
| 3×3 | 0.0006 | 0.0004 | -36.7% | 9 |
| 5×5 | 0.0013 | 0.0009 | -32.2% | 25 |
| 13×13 | 0.0073 | 0.0053 | -27.3% | 169 |
| 25×25 | 0.0252 | 0.0214 | -15.0% | 625 |

3×3을 1배로 두고 비교하면 이렇다.

| 크기 | 연산 횟수 배율 | 실측 시간 배율 |
|---|---|---|
| 3×3 | ×1.0 | ×1.0 |
| 5×5 | ×2.8 | ×2.1 |
| 13×13 | ×18.8 | ×11.9 |
| 25×25 | ×69.4 | ×41.2 |

`mac()`은 바깥 반복문이 N번, 안쪽 반복문이 N번 돌아서 곱셈과 덧셈이 정확히
N²번 일어난다. 그래서 시간 복잡도는 **O(N²)**이다. 여기서 N은 한 변의 길이이고,
칸 수 자체를 입력 크기로 보면 칸 수에 정비례하는 선형 연산이다.

**실측과 이론을 어떻게 연결했는가.** 실측 배율(×42.0)이 연산 배율(×69.4)보다
작아서 언뜻 N²보다 느리게 증가하는 것처럼 보인다. 하지만 실제 시간은
연산 시간만이 아니라 함수 호출과 반복문 준비에 드는 **고정 비용**을 포함한다.
그래서 모양을 아래처럼 놓고 네 측정값에 최소제곱으로 맞춰봤다.

```
시간(ms) = 고정 비용 + 곱셈 1회당 비용 × N²
```

| | 값 |
|---|---|
| 고정 비용 | 0.0003 ms |
| 곱셈 1회당 비용 | 39.9 ns |

이 식으로 되돌려 계산한 값과 실측값을 비교하면 이렇다.

| 크기 | N² | 실측(ms) | 모델(ms) | 오차 |
|---|---|---|---|---|
| 3×3 | 9 | 0.0006 | 0.0007 | +15.0% |
| 5×5 | 25 | 0.0013 | 0.0013 | +2.7% |
| 13×13 | 169 | 0.0073 | 0.0071 | -2.3% |
| 25×25 | 625 | 0.0252 | 0.0253 | +0.2% |

5×5 이상에서는 오차가 3% 안쪽이다. 3×3만 15% 벗어나는데,
전체 시간이 0.0006 ms라 고정 비용 0.0003 ms가 절반을 차지하기 때문이다.
곱셈 9번에 드는 시간과 함수를 부르고 반복문을 준비하는 시간이 비슷하다는 뜻이다.

즉 **실측 배율이 연산 배율보다 작아 보이는 것은 N² 법칙이 깨져서가 아니라,
작은 크기에서 고정 비용이 섞여 들어가기 때문이다.** 고정 비용을 분리하고 나면
곱셈 1회당 비용이 39.9 ns로 크기에 상관없이 일정하고, 이것이 N²에 비례한다.
이 모델이 실제로 맞는지는 5절에서 100배 큰 입력으로 확인했다.

1차원 버전은 2차원 버전보다 전 구간에서 빨랐다(이 실행에서 15~37% 감소).
곱셈 횟수는 똑같으므로 줄어든 건 연산량이 아니라 메모리 접근 단계다.
감소폭이 크기마다 다른 것은 측정 편차 때문이기도 해서,
정확한 값보다는 "같은 복잡도 안에서 상수만 줄었다"는 방향으로 보는 게 맞다.

- 측정 환경: macOS 27.0.1 (arm64), Python 3.14.8.
- **실행할 때마다 값이 흔들린다.** 같은 기기, 같은 코드인데도 다른 작업이

  그래서 절대 시간보다 같은 실행 안에서의 크기별 비율을 근거로 삼았다.

| 항목 | 이전에 조용했을 때 | 이 문서의 표 | 재현되는가 |
|---|---|---|---|
| 3×3 시간 | 0.0003 ms | 0.0006 ms | 아니오 (2배) |
| 25×25 시간 | 0.0126 ms | 0.0252 ms | 아니오 (2배) |
| 1000×1000 시간 | 21.9 ms | 43.3 ms | 아니오 (2배) |
| 25×25 시간 배율 | ×42.0 | ×41.2 | 예 |
| 모델의 25×25 오차 | +0.1% | +0.2% | 예 |
| 모델의 1000×1000 외삽 오차 | −9% | −8% | 예 |

다른 기기에서 돌려 시간이 달라져도 분석은 그대로 성립한다.
거꾸로 말하면 **표의 ms 값 자체는 이 기기의 그때 상태를 적어둔 것일 뿐**이다.

## 5. 대규모 입력에서의 한계

미션이 요구하는 크기는 최대 25×25지만, 이 구현이 어디까지 버티는지 확인하려고
100×100부터 1000×1000까지 같은 코드(`print_performance`, `print_optimization`)로 측정했다.

### 5-1. 측정 결과

| 크기 | 연산 횟수 (N²) | 2차원(ms) | 1차원(ms) | 변화율 | 4-3 모델 예측(ms) | 모델 오차 | 처리량 |
|---|---|---|---|---|---|---|---|
| 100×100 | 10,000 | 0.393 | 0.361 | -8.2% | 0.399 | +2% | 25 M MAC/s |
| 250×250 | 62,500 | 2.456 | 2.210 | -10.0% | 2.494 | +2% | 25 M MAC/s |
| 500×500 | 250,000 | 10.531 | 8.714 | -17.3% | 9.974 | -5% | 24 M MAC/s |
| 1000×1000 | 1,000,000 | 43.310 | 34.242 | -20.9% | 39.897 | -8% | 23 M MAC/s |

**O(N²)이 실제로 성립한다.** 4-3절의 모델은 3×3~25×25, 즉 연산 횟수 9~625회
구간의 측정값만으로 만든 것이다. 그 모델이 연산 횟수 1,000,000회인
1000×1000의 실제 시간을 8% 오차로 맞힌다. 연산 횟수가 1600배 늘어난 지점까지
외삽해도 어긋나지 않는다는 것이 N² 비례의 직접적인 근거다.

처리량이 25에서 23 M MAC/s로 조금씩 떨어지는 것은, 행렬이 커지면서
CPU 캐시에 다 들어가지 않아 메모리에서 읽어오는 비용이 늘기 때문이다.
25×25 행렬 두 개는 수 KB라 캐시에 통째로 올라가지만,
1000×1000 두 개는 16.9 MB라 그럴 수 없다.

### 5-2. 메모리

행렬 하나를 만들 때 쓰는 메모리를 각각 따로 측정했다(`tracemalloc` 최대 사용량).

| 1000×1000 행렬 | 메모리 |
|---|---|
| 0과 1만 쓰는 2차원 리스트 (`make_x`) | 8.45 MB |
| 값이 전부 다른 2차원 리스트 | 31.34 MB |

같은 크기인데 3.7배 차이가 난다. `make_x`가 쓰는 `0.0`과 `1.0`은
함수 안에 적힌 상수라 파이썬이 객체 하나를 만들어 전부 공유한다
(`make_x(5)[0][0] is make_x(5)[1][1]`이 `True`다).
그래서 실제로 메모리를 쓰는 것은 100만 개의 포인터(8바이트 × 100만 = 7.6 MB)뿐이다.

값이 전부 다르면 실수 객체 100만 개가 따로 생겨 24 MB가 더 붙는다.
**즉 이 데이터가 가벼운 것은 크기 덕이 아니라 0과 1만 쓰기 때문이다.**
실제 신경망 가중치처럼 전부 다른 실수가 들어오면 1000×1000 하나에 31 MB,
두 개면 62 MB가 필요하다. 1만×1만이면 같은 비율로 6 GB가 되어 메모리부터 막힌다.

### 5-3. 우선 검토할 최적화

1000×1000 입력으로 네 가지를 같은 조건에서 재봤다.

| 방식 | 시간 | 기준 대비 | 결과 |
|---|---|---|---|
| 2차원 리스트 (현재 `mac`) | 43.02 ms | 기준 | |
| 1차원 리스트 (현재 `mac_flat`) | 34.55 ms | **-20%** | 효과 있음 |
| `array('d')` 1차원 | 58.40 ms | **+36%** | 오히려 느려짐 |
| 0인 칸 건너뛰기 | 23.11 ms | **-46%** | 가장 효과 큼 |

네 방식 모두 같은 값(3.0)을 돌려주는 것을 확인했다.

**1) 메모리 레이아웃 — 1차원으로 펴기 (효과 있음, -21%).**
이미 구현해둔 보너스다. 25×25에서 -15%였던 효과가 1000×1000에서 -20%로
커진다. 크기가 클수록 메모리 접근 비용의 비중이 커지기 때문이다.

**2) 반복 축소 — 0인 칸 건너뛰기 (가장 효과 큼, -48%).**
이 데이터의 패턴은 1000×1000 중 값이 0이 아닌 칸이 2,000개뿐이다(전체의 0.20%).
곱셈 결과가 0이면 합에 영향이 없으므로 건너뛰어도 결과가 같다.

```python
for i, value in enumerate(flat_pattern):
    if value:
        total += value * flat_filter[i]
```

분기가 하나 늘었는데도 두 배 가까이 빨라진다. 99.8%의 칸에서 곱셈과
덧셈을 건너뛰기 때문이다. 다만 **입력에 0이 거의 없으면 분기 비용만 늘어
오히려 느려진다.** 희소한 입력이라는 사실을 알 때만 쓸 수 있는 방법이고,
시간 복잡도도 O(N²)에서 O(0이 아닌 칸 수)로 성격이 바뀐다.
미션 데이터가 0/1 패턴이라 효과가 극적으로 보이는 것이므로,
일반적인 최적화로 제시하기는 어렵다고 판단해 기본 구현에는 넣지 않았다.

**3) `array('d')` — 측정해보니 역효과 (+36%).**
실수를 C 배열에 담으면 객체 오버헤드가 사라져 메모리가 줄 것이라고 예상했는데,
시간은 오히려 36% 늘었다. `array('d')`에서 값을 하나 꺼낼 때마다
파이썬 실수 객체를 새로 만들기 때문이다(boxing). 리스트는 이미 만들어진
객체의 포인터만 넘기므로 그 비용이 없다.
**메모리를 줄이려다 속도를 잃는 교환이고, 순수 파이썬에서는 손해다.**

**4) 블록 처리(타일링) — 이 구현에서는 의미 없음.**
큰 행렬을 캐시에 들어가는 작은 덩어리로 잘라 처리하는 기법이다.
행렬 곱셈처럼 같은 데이터를 여러 번 읽는 연산에서 효과가 크다.
하지만 MAC은 각 칸을 **정확히 한 번씩만** 읽고 끝나므로 재사용할 것이 없다.
잘라도 읽는 횟수가 그대로라 이득이 없어 시도하지 않았다.

**정리하면 우선순위는 이렇다.**

1. 1차원 레이아웃 (-20%). 입력 성격과 무관하게 항상 적용 가능하다.
2. 희소성 활용 (-46%). 입력에 0이 많을 때만. 효과는 가장 크지만 조건부다.
3. 메모리가 먼저 문제가 되면 값 표현을 바꿔야 한다. 다만 `array('d')`처럼
   순수 파이썬 안에서의 교체는 속도를 잃으므로, 이 지점부터는
   벡터화 라이브러리나 전용 하드웨어로 넘어가는 것이 맞다(6절).
4. 블록 처리는 MAC 단독 연산에는 적용 대상이 아니다.

## 6. MAC 연산이 AI에서 중요한 이유와 CPU/NPU 병목

### 6-1. MAC이 신경망의 기본 연산인 이유

신경망의 핵심 연산은 두 가지인데 둘 다 MAC의 반복이다.

- **완전연결층**: 출력 하나는 `입력들 × 가중치들`을 전부 곱해 더한 값이다.
  이것이 MAC 그 자체다. 입력 1000개, 출력 1000개인 층 하나에 MAC 100만 번이 든다.
- **합성곱층**: 필터를 입력 위에서 한 칸씩 옮기며, 겹치는 부분끼리
  곱해 더한다. 겹치는 부분의 계산 한 번이 정확히 MAC 한 번이다.

**이 프로그램의 모드 1이 바로 합성곱 한 칸이다.** 3×3 필터와 3×3 입력을
위치별로 곱해 더해서 숫자 하나를 얻는 과정은, 합성곱층이 출력 한 칸을
만드는 과정과 같다. 다른 점은 실제 합성곱은 이것을 입력 전체에 대해
수백만 번 반복하고, 필터도 하나가 아니라 수십~수백 개라는 것뿐이다.

그래서 신경망 실행 시간의 대부분은 MAC을 몇 번 하느냐로 결정된다.
MAC 한 번을 얼마나 빨리 하느냐, 그리고 몇 개를 동시에 하느냐가 곧 성능이다.

### 6-2. CPU와 NPU의 구조적 차이

| | CPU | NPU |
|---|---|---|
| 설계 목표 | 아무 종류의 명령이나 빠르게 | MAC을 아주 많이 동시에 |
| 연산 유닛 | 코어당 소수의 범용 연산기 | MAC 전용 유닛을 격자로 다수 배치 |
| 실행 방식 | 명령을 하나씩 해석해 실행 | 데이터를 격자에 흘려보내며 동시 계산 |
| 강점 | 분기, 다양한 자료형, 범용성 | 같은 연산의 대량 반복 |
| 약점 | 동시에 할 수 있는 MAC 수가 적음 | MAC 외의 일은 못 하거나 비효율 |

CPU는 분기 예측, 캐시 계층, 비순차 실행 같은 장치를 써서
**한 줄기 명령 흐름**을 빠르게 만든다. 반면 NPU는 그런 장치를 덜어내고
그 자리에 MAC 유닛을 채워 **같은 연산을 동시에 많이** 하도록 만든다.
가중치를 한 번 올려놓고 여러 입력을 흘려보내 재사용하는 구조가 대표적이다.

### 6-3. 병목이 어디에서 생기는가

병목은 단계마다 다르고, 이 프로그램의 측정값으로 앞 두 단계를 직접 확인할 수 있다.

**(1) 인터프리터 병목 — 순수 파이썬.**
측정한 처리량은 23~25 M MAC/s, 곱셈 1회당 약 40 ns다.
그런데 요즘 CPU는 코어 하나로 1초에 수십억 번의 부동소수점 곱셈을 처리한다.
즉 **곱셈 자체가 아니라 파이썬이 명령을 해석하고 객체를 다루는 비용이
시간의 대부분**이다. 5-3절에서 `array('d')`가 오히려 36% 느려진 것이
이 병목의 직접적인 증거다. 메모리를 아껴도 객체를 새로 만드는 비용이
그 이득을 넘어버린다.

**(2) 메모리 병목 — 최적화된 CPU 코드.**
인터프리터 비용을 걷어내면 다음 벽은 메모리다.
MAC은 **연산 강도가 매우 낮다.** 곱셈-누적 한 번(연산 2회)을 하려고
8바이트짜리 값을 두 개(16바이트) 읽어야 한다. 연산/바이트 비율이 0.125로,
읽어오는 속도가 계산 속도를 따라가지 못한다.
이 프로그램에서도 크기가 커질수록 처리량이 25에서 23 M MAC/s로 떨어지고,
1차원으로 펴서 접근 단계를 줄이면 20% 빨라진다. 둘 다 연산량은 그대로인데
메모리 접근만 바뀌어 생긴 차이라, 메모리 쪽에 여유가 없다는 뜻이다.

**(3) 데이터 공급 병목 — NPU.**
NPU는 MAC 유닛을 대량으로 깔아 (1)과 (2)의 연산 측 한계를 넘는다.
그러면 병목은 더 확실하게 **유닛에 데이터를 얼마나 빨리 넣어주느냐**로 옮겨간다.
연산 유닛이 많아질수록 같은 시간에 더 많은 데이터가 필요한데
메모리 대역폭은 그만큼 늘지 않기 때문이다. 그래서 NPU 설계는
데이터 재사용(한 번 올린 가중치를 여러 입력에 쓰기)과
낮은 정밀도(실수 대신 8비트 정수를 써서 읽을 바이트 수를 줄이기)에 집중한다.

### 6-4. 무엇을 재고 어떻게 비교할 것인가

| 지표 | 뜻 | 이 프로그램에서 |
|---|---|---|
| 처리량 (MAC/s) | 초당 처리한 곱셈-누적 횟수 | 23~25 M MAC/s |
| 연산 강도 (연산/바이트) | 읽은 바이트당 연산 수 | 2 / 16 = 0.125 (매우 낮음) |
| 고정 비용 | 크기와 무관한 호출 비용 | 0.0003 ms (4-3절) |
| 크기별 처리량 변화 | 캐시를 벗어나는 지점 | 25 → 23 M MAC/s |

**비교할 때 지켜야 할 것.**

- 절대 시간이 아니라 **처리량(MAC/s)으로 환산**해서 비교한다.
  크기가 다르면 연산 횟수가 달라 시간을 직접 비교할 수 없다.
  이 문서의 5-1절 표가 그렇게 만들어졌다.
- **같은 입력, 같은 반복 횟수**로 잰다. 5-3절의 네 방식 비교는
  모두 같은 1000×1000 입력에 같은 반복 횟수를 썼고,
  결과값이 전부 3.0으로 같은지 먼저 확인한 뒤 시간을 비교했다.
- **고정 비용을 분리**한다. 작은 입력에서는 고정 비용이 전체를 가려
  연산 성능을 비교할 수 없다(3×3에서 모델 오차가 20%인 이유).
- 측정은 실행마다 흔들리므로 **여러 번 재서 중앙값**을 쓴다.
  이 문서의 수치는 `benchmark.py` 한 번 실행에서 나온,
  5회(대규모는 3회) 측정의 중앙값이다.

### 6-5. 이 구현의 위치

정리하면 이 프로그램은 **MAC이 무엇인지 보여주는 구현이지
빠른 구현이 아니다.** 측정된 23~25 M MAC/s는 전용 하드웨어는 물론
같은 연산을 C로 짠 것과도 비교 대상이 아니다.
외부 라이브러리 금지가 미션 조건이라 그렇게 만든 것이고,
덕분에 "MAC 한 번에 드는 비용"과 "메모리 접근을 바꾸면 생기는 차이"를
숫자로 직접 볼 수 있었다. 5-3절과 6-3절의 분석은 전부 그 측정에서 나왔다.

## 7. 알고 있는 한계

- `mac()`은 정사각 행렬만 다룬다. `len(pattern)`으로 한 변의 길이를 잡기 때문에
  직사각형을 넣으면 앞쪽 일부만 계산한다. 미션 범위가 N×N이라 그대로 뒀고,
  대신 `is_square()`로 데이터를 받을 때 정사각인지 먼저 확인한다.
- 붙여쓴 입력(`010`)은 모든 글자가 숫자일 때만 쪼갠다(3-1절).
  `0.5 0.5 0.5`처럼 소수를 붙여 쓸 수는 없고, 공백으로 구분해야 한다.
- 성능 측정값은 같은 기기에서도 실행할 때마다 흔들린다(4-4절).
  10회 평균은 미션 최소 기준을 맞춘 것이고, 통계적으로 안정된 값은 아니다.
  워밍업 1회는 순서를 섞어 다시 재서 "효과가 확인되지 않는다"까지는
  확인했지만(3-5절), 그건 25×25 이하에서의 결과다. 캐시에 들어가지 않는
  큰 입력에서도 같은지는 재보지 않았다.
- 모드 1은 3×3 고정이다. 임의 크기 입력은 모드 3에서 받는다.
- 패턴 생성기는 짝수 N에서 두 필터의 1인 칸 수가 달라진다(3-6절).
  모드 3에서 짝수를 막아 두긴 했지만 `make_cross`와 `make_x` 자체는
  짝수도 만들어 준다. 공평하게 만들려면 필터 정규화가 필요한데
  점수의 의미가 달라져서 미션 범위를 벗어난다고 보고 넣지 않았다.
- 라벨이 Cross와 X 두 개라는 전제가 `decide()`에 박혀 있다.
  세 개 이상으로 늘리려면 비교 로직을 바꿔야 한다(3-2절에 절차를 적었다).
- 점수는 정규화되지 않아 서로 다른 크기나 패턴 사이의 비교에는 쓸 수 없다(3-1절).
